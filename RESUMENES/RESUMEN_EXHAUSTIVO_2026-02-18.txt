**RESUMEN EJECUTIVO**

Este documento sintetiza una revisión técnica exhaustiva del proyecto Kool TPV v2 realizada el 2026-02-18. Se mantiene el formato y la estructura del resumen previo (2026-02-17) para facilitar comparaciones y auditorías.

---

**ESTRUCTURA DEL REPOSITORIO (alto nivel)**
- Raíz:
  - `main.py` -> arranque de la aplicación (CTk/Tkinter UI).
  - `requirements.txt` -> dependencias principales.
  - `kool_tpv/` -> paquete principal con módulos, base de datos, assets, utilidades.
  - `RESUMENES/` -> contiene archivos de resumen y guía de estilo.
  - `scripts/` y `tests/` -> casos de prueba y scripts de apoyo.

- Dentro de `kool_tpv`:
  - `base_datos/` -> servicios y wrappers para SQLite (db_wrapper, db_init, servicios por entidad).
  - `modulos/` -> implementaciones funcionales (tpv, almacen, clientes, impresion, configuracion, etc.).
  - `utils/` -> componentes UI reutilizables, formateo, diálogos personalizados, templates UI.
  - `assets/` -> recursos gráficos y fuentes.
  - `config/` -> configuraciones JSON (botones, menús).

---

**ARRANQUE Y FLUJO PRINCIPAL**

- `main.py` (raíz) realiza:
  - Configuración de `customtkinter`, logging y carpetas de logs.
  - Inicialización de la base de datos mediante `initialize_database(db_path)` y `Database.connect()`.
  - Construcción de la UI principal y barra lateral con botones cargados desde `config/buttons_config.json`.
  - Instanciación y carga de `TpvView` y demás módulos mediante lazy imports.

Observaciones:
- Buena separación entre inicialización y carga de módulos (lazy imports).
- Uso extensivo de try/except mejora robustez pero puede ocultar errores si logs carecen de contexto.

---

**BASE DE DATOS Y PERSISTENCIA**

- `kool_tpv/base_datos/db_wrapper.py`:
  - Wrapper `Database` con métodos `connect`, `execute_query`, `fetch_all`, `fetch_one`, `close_connection` y `transaction()` context manager.
  - Defaults mitigantes de concurrencia: `check_same_thread=False`, `timeout=10`.

- `kool_tpv/base_datos/db_init.py`:
  - `initialize_database(db_path)` aplica `migraciones/base.sql` cuando faltan tablas críticas y verifica post-migración.

Observaciones:
- `Database.transaction()` y `ticket_service.save_ticket` implementan operaciones atómicas críticas.
- Revisar `migraciones/base.sql` para confirmar tablas opcionales (payments, audit_logs, stock_movements, points_movements, etc.).

  -- trigger trg_ticket_lines_after_delete
  CREATE TRIGGER trg_ticket_lines_after_delete
  AFTER DELETE ON ticket_lines
  BEGIN
    UPDATE tickets SET num_ventas = COALESCE((SELECT COUNT(*) FROM ticket_lines WHERE ticket_id = OLD.ticket_id),0) WHERE id = OLD.ticket_id;
  END
  
  -- trigger trg_ticket_lines_after_insert
  CREATE TRIGGER trg_ticket_lines_after_insert
  AFTER INSERT ON ticket_lines
  BEGIN
    UPDATE tickets SET num_ventas = COALESCE((SELECT COUNT(*) FROM ticket_lines WHERE ticket_id = NEW.ticket_id),0) WHERE id = NEW.ticket_id;
  END
  
  -- trigger trg_ticket_lines_after_update_ticketid
  CREATE TRIGGER trg_ticket_lines_after_update_ticketid
  AFTER UPDATE OF ticket_id ON ticket_lines
  BEGIN
    UPDATE tickets SET num_ventas = COALESCE((SELECT COUNT(*) FROM ticket_lines WHERE ticket_id = OLD.ticket_id),0) WHERE id = OLD.ticket_id;
    UPDATE tickets SET num_ventas = COALESCE((SELECT COUNT(*) FROM ticket_lines WHERE ticket_id = NEW.ticket_id),0) WHERE id = NEW.ticket_id;
  END

- PROMPT DE BLINDAJE ARQUITECTÓNICO Y UI (ESTÁNDAR KOOL_V2)
- ══════════════════════════════════════════════════════════
- 
- OBJETIVO:
- Consolidar la identidad visual Matrix y blindar la lógica de validación de datos. A partir de ahora, todo el sistema debe regirse por estos estándares inamovibles.
- 🎨 1. BLINDAJE ESTÉTICO (SISTEMA DE DISEÑO)
- 
- Para asegurar que todos los módulos (Almacén, Clientes, Shopify, etc.) sean idénticos, debes aplicar estos valores fijos en utils/templates/base_module_view.py:
- 
-     Sidebar (Inamovible): Ancho fijo de 220px. Fondo #393E46.
- 
-     Zona Central (Fondo): Siempre #1a1a1a (Negro profundo).
- 
-     Sistema de Ruta (Breadcrumbs): Implementar en la parte superior de la zona central un CTkLabel persistente que muestre la ruta: SISTEMA_KOOL_TPV: / [MODULO] / [SUB_SECCION].
- 
-         Fuente: Courier New, 12px, negrita. Color: #00FF00.
- 
-     Cero Flicker: Todas las pestañas (Tabs) y frames de contenido deben tener fg_color="#1a1a1a" para garantizar transiciones totalmente negras.
- 
- ⌨️ 2. BLINDAJE DE BUSCADORES (SearchableCombo PRO)
- 
- Debes refactorizar el componente SearchableCombo para que sea una herramienta de alta productividad:
- 
-     Navegación Remota (Sin pérdida de foco):
- 
-         Las flechas Arriba/Abajo y la tecla Enter deben controlar la lista de sugerencias sin que el cursor abandone el Entry.
- 
-         El evento KeyRelease debe ignorar estas teclas de navegación para no regenerar la lista mientras se navega.
- 
-     Validación Estricta (Strict Mode):
- 
-         Al dispararse el evento FocusOut (salir del campo), el componente debe verificar si el texto existe en la base de datos.
- 
-         Si es inválido: Cambiar el border_color a Rojo (#FF0000) inmediatamente.
- 
-         Si es válido: Mantener el border_color en Verde (#00FF00).
- 
- 📊 3. ESTÁNDAR DE FORMULARIOS (GRID 8 COLUMNAS)
- 
- Todos los formularios complejos (como Crear Producto) deben usar un Grid de 8 columnas para una alineación perfecta.
- 
-     Usar columnspan para equilibrar filas (ej. ID: 2 col, Nombre: 6 col).
- 
-     Las etiquetas (Labels) deben usar siempre la fuente Courier New en verde.
- 
-     Los cuadros de texto largos (SEO Description, Descripción Web) deben ser CTkTextbox.
- 
- 💾 4. BLINDAJE DE DATOS (TRANSACCIONES SQL)
- 
- El botón de Guardado debe ser atómico. No se permite guardar un producto si su precio falla.
- 
-     Validación Previa: Si algún SearchableCombo tiene el borde en Rojo (inválido) o get_id() es None, el guardado se aborta con un show_error.
- 
-     Atomicidad: Usar BEGIN TRANSACTION y COMMIT para asegurar que las tablas productos y precios se actualicen simultáneamente.
- 
- ✅ CRITERIO DE ACEPTACIÓN FINAL:
- 
-     La navegación por el almacén es fluida y muestra la ruta arriba: ALMACEN / CREAR.
- 
-     No es posible guardar una categoría inexistente (como "Libretilla").
- 
-     El usuario puede rellenar todo el formulario usando solo el teclado (Tab, flechas y Enter).
- 
-     Visualmente, la app es consistente: 220px de sidebar y estética Matrix impecable.

**ANÁLISIS DE PROS Y CONTRAS**
Pros:
- Arquitectura modular clara y servicios encapsulados.
- Uso de transacciones en operaciones críticas.
- Componentes reutilizables y manejo opcional de impresión.

Contras:
- Archivos UI extensos con mezcla de responsabilidades.
- Uso de SQLite limita concurrencia en entornos multi-proceso.
- Falta de tipado consistente y pruebas en `save_ticket`.

---

**RECOMENDACIONES Y FUTURAS IMPLEMENTACIONES**
- Refactorizar `TpvView` por responsabilidades.
- Implementar validación estricta en `SearchableCombo` según guía.
- Añadir pruebas unitarias/integración para `save_ticket` y `CarritoService` (usar DB :memory: para tests).
- Establecer estrategia de migraciones incremental y considerar migración a RDBMS si se necesita concurrencia real.
- Forzar uso consistente de `Decimal` y normalizar almacenamiento de valores monetarios.

Archivo: kool_tpv/base_datos/ticket_service.py
 - Doc: Ticket persistence service.
 - Área funcional: carrito, clientes, configuracion, fidelizacion, impresion, persistencia, productos, ticket
 - Funciones top-level: save_ticket
 - Descripción detallada (manual):
   - Propósito: Persiste un ticket completo en la base de datos de forma atómica. Inserta
     registros en `tickets`, `ticket_lines`, registra `payments`, actualiza `productos`
     (`stock_actual`, `ventas_totales`), crea entradas en `stock_movements` y `points_movements`
     y actualiza la cuenta de fidelización del cliente si procede.
   - Flujo clave:
     1. Valida conexión y obtiene próximo `num_ticket` mediante `SELECT MAX(num_ticket)`.
     2. Calcula puntos de fidelización (delegando a `FidelizacionService`).
     3. Inserta el registro principal en `tickets` y obtiene `ticket_id`.
     4. Inserta cada línea en `ticket_lines`, aplica cambios en `productos` y registra `stock_movements`.
     5. Inserta líneas de descuento distribuidas por tipo de IVA si aplica.
     6. Inserta `payments` desglosados y escribe un entry en `audit_logs` si existen las tablas.
     7. Actualiza `clientes` (tesoro/tesoro_historico/tesoro_gastado_total) y recalcula `id_nivel`.
     8. Genera snapshot `ticket_text` usando `VentaTicketGenerator` cuando esté disponible.
   - Puntos críticos y riesgos:
     - Uso de `SELECT MAX(num_ticket)` para generar el número de ticket puede causar colisiones
       en entornos con concurrencia multi-proceso; considerar secuencia centralizada.
     - Se mezclan `Decimal` y conversiones a `str()` para inserciones: es deliberado pero requiere
       comprobación consistente en lecturas (tipos en DB y en servicios consumidores).
     - El código silencia errores de tablas opcionales (payments, audit_logs) mediante excepts,
       lo cual es tolerante pero puede ocultar falta de integridad en entornos mal provisionados.
   - Recomendaciones:
     - Añadir tests unitarios/integración para casos: venta normal, devolución, descuento por IVA,
       canje de puntos y concurrencia de tickets.
     - Considerar mecanismo alternativo para `num_ticket` (tabla `counters` o usar `rowid`).
