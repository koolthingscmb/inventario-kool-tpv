RESUMEN EJECUTIVO (1-2 párrafos)

KOOL_TPV_V2 es una aplicación TPV de escritorio escrita en Python con UI basada en `customtkinter`. La arquitectura separa claramente: vistas (UI), servicios (persistencia/impresión), lógica de negocio (CarritoService) y controladores de acciones (cash/tarjeta/multi pago). Durante la mañana se implementaron y reforzaron los flujos de cobro, la persistencia de tickets y la generación/impresión de tickets (simulada), además de arreglar bugs de formato y consolidar el manejo de importes mixtos.

Se han tomado decisiones concretas:
- Mantener `Decimal` para cálculos en memoria; serializar a string al persistir para evitar conversión implícita a float en SQLite.
- Implementar impresión en texto plano con `TicketGenerator` y un `ImpresoraService` simulado para permitir verificación sin impresora física.
- Soportar pagos mixtos (efectivo+tarjeta) y persistir desgloses en `ticket_service.save_ticket`.

File: kool_tpv/modulos/impresion/ticket_generator.py
----------------------------------------------------------------------
Propósito:
- Generador de tickets en texto plano con anchura fija `WIDTH=42`.

API pública:
- `TicketGenerator._format_currency(val) -> str` (2 decimales)
- `TicketGenerator.generate(config, ticket_data, items, cliente_data=None) -> str`

Diseño y secciones generadas:
- Encabezado (centrado): `nombre_negocio`, `direccion`, `nif`.
- Info venta: `FACTURA SIMPLIFICADA`, `Fecha Hora - Cajero - Ticket: Num`.
- Cuerpo: cabecera `Cant | Articulo | PVP | Total` y líneas por item (truncado del nombre para encajar).
- Tesoro: línea adicional si `tesoro_data['gastado'] > 0`.
- Resumen financiero: Subtotal, lista de IVAs (`iva_desglose` dict o lista), `DOUBLE_DIVIDER`, TOTAL (alineado), `DOUBLE_DIVIDER`.
- Tabla de pagos: 4 columnas con anchos fijos (9,10,10,10) para encajar en 42 chars. Soporta:
   * Pago normal: una fila con formaPago | total | entregado | devuelto
   * Pago Mixto: dos filas — Efectivo (Total=importe_efectivo, Entr.=importe_efectivo, Dev.=0.00) y Tarjeta (Total=importe_tarjeta, Entr.=importe_tarjeta, Dev.=0.00)
- Fidelización: si `cliente_data` presente, mostrar nombre centrado, nivel alineado a la derecha y desglose de tesoro.
- Pie: `I.V.A Incluido` y `pie_texto` centrado.

Implementación técnica relevante (correcciones y mejoras realizadas):
- Añadido manejo robusto para nombres de campos alternativos (`cantidad`, `cant`, `qty`) y para `precio`/`pvp`.
- Eliminados espacios problemáticos dentro de especificadores en f-strings para evitar `ValueError`.
- Cálculo de total por línea con `Decimal(pvp) * Decimal(cantidad)` cuando `total` no está presente.
- Introducida función interna `fmt()` que delega a `_format_currency` para mantener coherencia.

Ejemplo de uso:
```py
gen = TicketGenerator()
texto = gen.generate(config, ticket_data, items, cliente_data)
print(texto)
```

Pruebas:
- Se generaron tickets mixtos y simples en desarrollo; verificar alineados y truncados con nombres largos.

Recomendación:
- Añadir tests unitarios que verifiquen límites de ancho y formatos con entradas edge-case.

3) `TpvView._on_finalize`:
   - Valida carrito no vacío.
   - Recupera `resumen_financiero` de `CarritoService`.
   - Captura `items_to_print` ANTES de persistir (para evitar imprimir carrito vacío).
   - Llama a `save_ticket` (persistencia) pasando `importe_efectivo`/`importe_tarjeta` cuando proceda.
   - Si `save_ticket` es exitoso, limpia el carrito y luego intenta imprimir (simulado) **usando los items capturados previamente**, todo envuelto en try/except para que errores de impresión no rompan el flujo.

PUNTOS CRÍTICOS Y RECOMENDACIONES (detallado)

1) Esquema de BD y migraciones
   - `save_ticket` ahora asume columnas adicionales; antes de desplegar a producción es obligatorio revisar el esquema y aplicar migración:
     * `ALTER TABLE tickets ADD COLUMN importe_efectivo TEXT DEFAULT '0'` (o similar)
     * `ALTER TABLE tickets ADD COLUMN importe_tarjeta TEXT DEFAULT '0'`
   - Alternativa: adaptar `save_ticket` para rellenar valores en columnas existentes o usar `INSERT INTO tickets (col1, col2, ...) VALUES (...)` solo con columnas existentes.

2) Consistencia monetaria
   - Homogeneizar el uso de `Decimal` en todo el stack y decidir la estrategia de almacenamiento monetario.

3) Concurrencia y `num_ticket`
   - `num_ticket` calculado con `MAX(num_ticket)+1` es susceptible a condiciones de carrera. Recomendado:
     * Usar una tabla de secuencia o mecanismo exclusivo en DB (fila de lock) o AUTOINCREMENT y almacenar `num_ticket` derivado de `id`.

4) Impresión
   - Implementación actual es una simulación por terminal. Para impresión física, añadir backend ESC/POS o CUPS y colas de impresión (queue) para no bloquear UI.

5) Tests y validación
   - Añadir tests unitarios e integrados:
     * `TicketGenerator.generate()` con escenarios: pago efectivo, tarjeta, mixto, cliente/no cliente, tesoro presente/no.
     * `save_ticket()` sobre base de datos temporal in-memory para validar inserciones y actualizaciones de stock.
     * Pruebas headless end-to-end para los controladores de pago en flows comunes.
