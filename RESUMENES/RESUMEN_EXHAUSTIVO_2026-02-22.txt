**RESUMEN EJECUTIVO**

Kool TPV v2 es una aplicación de punto de venta escrita en Python con UI en
`customtkinter`. La aplicación está organizada como un paquete `kool_tpv` que
contiene: lógica de persistencia (SQLite), servicios por entidad (producto,
ticket, albarán, proveedor, tipos, categorías), módulos de UI por área
(TPV, Almacén, Clientes, Impresión) y utilidades (formatters, diálogos,
componentes reutilizables). La base de datos principal es `kool_bd.db` ubicada en
`kool_tpv/base_datos/`.

La arquitectura es pragmática y modular: los servicios de acceso a datos están
separados en `base_datos`, la UI se encuentra en `modulos` y las utilidades en
`utils`. Sin embargo, aparecen puntos repetidos y mezclas de lógica/ presentación
en archivos UI extensos (p. ej. `tpv_view.py`). En la persistencia se usan
transacciones y triggers; la numeración de tickets usa `SELECT MAX(num_ticket)`
lo que comporta riesgo de colisiones en entornos concurrentes.

Objetivo de este documento: describir qué hace cada componente principal,
documentar el schema de la base de datos, evaluar estado y riesgos, y proponer
mejoras con prioridad.

**INVENTARIO (resumen de la estructura principal)**

- `main.py` (raíz): entrypoint de arranque; delega a `kool_tpv/main.py` si se
  ejecuta desde editor.
- `kool_tpv/` (paquete principal): contiene subcarpetas:
  - `base_datos/`: wrapper DB, inicialización y servicios por entidad

  - `modulos/`: UI y orquestación por áreas (tpv, almacen, clientes, impresion,

  - `utils/`: componentes UI reutilizables (`custom_dialog.py`,
    `formatter_service.py`, `config_loader.py`, `keyboard_manager.py`,

  - `config/`: JSONs que parametrizan botones y menús (`buttons_config.json`,
    `buttons_actions_config.json`, `buttons_menu.json`, `colors_config.json`)
  - `assets/`: iconos, fuentes y imágenes usadas por la UI

Nota: existen backups de la DB (`kool_bd.db.bak`, etc.) pero la migración
activa está en `migraciones/base.sql`.

---

**FLUJO DE ARRANQUE**

1. `main.py` (raíz) o `kool_tpv/main.py` detecta proyecto y ejecuta `main.py`.
2. Inicialización de logging y llamada a `initialize_database(db_path)` si la DB
   no existe o faltan tablas.
3. `App` (UI principal) construye sidebar y cargador de módulos; lee
   `config/buttons_config.json` para los botones de la interfaz.
4. Los módulos se importan laxamente (lazy import) cuando se solicitan (TPV,
   Almacén, Clientes...).
5. La capa `base_datos.Database` centraliza la conexión SQLite y provee
   `transaction()` para operaciones atómicas.

Componentes críticos en arranque:
- `kool_tpv/base_datos/db_init.py`: aplica `migraciones/base.sql` si faltan tablas.
- `kool_tpv/base_datos/db_wrapper.py`: establece `check_same_thread=False` y
  `.row_factory = sqlite3.Row`.

**REVISIÓN POR CAPAS - HALLAZGOS CLAVE**

1) Persistencia (`base_datos`)
- `db_wrapper.Database`:
  - Provee `connect()`, `execute_query`, `fetch_all`, `fetch_one`, `transaction()`.
  - `check_same_thread=False` permite acceso desde hilos, pero no gestiona
    concurrencia a nivel proceso; correctos `timeout=10` y manejo de commit/rollback.
  - Recomendación: instrumentar logs de queries lentas y asegurar cierre de
    conexión en finalización.

- `db_init.py`:
  - Lógica de migraciones: detecta tablas críticas (`productos`, `tickets`,
    `cierres_caja`) y ejecuta `migraciones/base.sql` si faltan.
  - Recomendación: versionar migraciones (tabla `schema_version`) para
    controlar upgrades incrementales.

- Servicios (`ticket_service.py`, `producto_service.py`, `albaran_service.py`, ...):
  - Patrón común: usar `db.fetch_one` y `db.fetch_all` y `db.execute_query`.
  - `ticket_service.save_ticket` es atómico (BEGIN ... COMMIT) y cubre:
    inserción en `tickets`, `ticket_lines`, `payments`, `stock_movements`,
    `points_movements` y actualización de `productos` y `clientes`.
  - Riesgos: `num_ticket` se genera usando `SELECT MAX(num_ticket)` — no es
    safe en concurrencia multi-terminal; sugiere usar tabla `counters` o
    migrar a DB con sequences.
  - `albaran_service.save_albaran` actualiza stock y calcula IVA; la rutina
    está bien encapsulada y usa transacción.
  - Buenas prácticas observadas: uso de Decimal para dinero en muchos puntos,
    inserciones de auditoría y fallback cuando tablas accesorias no existen.

2) UI / Modulos
- `modulos/tpv/tpv_view.py` (archivo extenso):
  - Implementa la vista principal del TPV, grid de botones (12) y panel derecho
    con carrito. Usa `load_button_config_from_json()` para parametrizar botones.
  - Contiene lógica de orquestación (despacho de acciones, finalización de
    pago y llamada a `save_ticket`) mezclada con código de construcción UI.
  - Recomendación: dividir en subcomponentes y mover la lógica de negocio a
    controladores/servicios para facilitar pruebas unitarias.

- `modulos/tpv/carrito/carrito_service.py`:
  - Maneja items, descuentos, canje de puntos, resumen financiero y cálculo
    de IVA. Usa Decimal y mantiene invariantes razonables.
  - Recomendación: cubrir con tests unitarios varias combinaciones de descuento,
    devoluciones y canje de puntos.

- Otros módulos (`almacen`, `clientes`, `impresion`):
  - Buen nivel de separación: `AlbaranService` maneja stock y líneas; `VentaTicketGenerator`
    genera snapshot textual para impresión.

3) Utils y Config
- `utils/formatter_service.py`: formatter consistente con Decimal y ROUND_HALF_UP,
  recomendado para mantener precisión financiera.
- `utils/custom_dialog.py`: diálogos modal con branding; bien encapsulado.
- `config/*.json`: parametrización de botones y menús; recomendable añadir
  validación schema JSON en arranque.

**ANÁLISIS DETALLADO POR ARCHIVO (selección de ficheros clave)**

Nota: se indican responsabilidad, áreas de riesgo y recomendaciones concretas.

- `main.py` (raíz):
  - Rol: punto de entrada para ejecución desde editor; delega a `main.py` raíz.
  - Mejora: añadir flag `--headless` para permitir arranque en CI/entornos de
    test sin GUI, y exponer `--db-path` para pruebas con `:memory:`.

- `kool_tpv/main.py` (package):
  - Simplifica ejecución desde IDE insertando el root en `sys.path`

- `kool_tpv/base_datos/db_wrapper.py`:
  - Context manager `transaction()` correcto; maneja commit/rollback.
  - Recomendación: agregar un método `execute_script()` para migraciones y
    métricas de latencia. Considerar `set_trace_callback` para debug SQL.

- `kool_tpv/base_datos/db_init.py`:
  - Aplica `migraciones/base.sql` si detecta tablas faltantes.
  - Recomendación: crear `schema_version` y migraciones incrementales para
    permitir upgrades seguros y reversibles.

- `kool_tpv/base_datos/ticket_service.py`:
  - Save_ticket: extensa función que cubre persitencia, stock, pagos, puntos,
    snapshot de impresión y auditoría. Ventajas: todo en una transacción.
  - Riesgos:
    * `SELECT MAX(num_ticket)` → race condition.
    * Inserciones en tablas accesorias (payments, audit_logs) capturan excepciones
      silenciosamente (se ignora si tabla no existe) — útil para resiliencia,
      pero puede ocultar bugs de DB mismatched schema.
  - Recomendaciones:
    * Sustituir generación de `num_ticket` por incrementador seguro (tabla counters
      o secuencia en DB servidor).
    * Añadir cobertura de tests de integración usando `:memory:` para simular
      fallos y concurrencia.

- `kool_tpv/base_datos/producto_service.py`:
  - Buenas consultas con LEFT JOIN en precios y codigos_barras; paginación bien
    implementada. Recomendación: indexar `productos.sku` y revisar consultas
    con GROUP_CONCAT para rendimiento en tablas grandes.

- `kool_tpv/base_datos/albaran_service.py`:
  - Implementa `save_albaran`, `update_albaran_with_new_lines` y filtros; realiza
    updates de stock. Buen uso de transacción y rollback.
  - Recomendación: documentar comportamiento de eliminación de albaranes y
    consecuencias sobre stock (nota en docstring ya presente: delete no revierte).

- `kool_tpv/base_datos/cierre_service.py`:
  - Calculo de totales para grupo de tickets y creación atómica de cierre.
  - Recomendación: testear grandes volúmenes y evaluar locking/timeout con
    SQLite WAL en escenarios concurrentes.

- `kool_tpv/modulos/tpv/tpv_view.py`:
  - Archivo muy rico en features pero demasiado largo; responsabilidades:
    UI layout, dispatcher de comandos, hooking a servicios (carrito, stock,
    devoluciones, cierre) y fin de pago.
  - Recomendación técnica: dividir en `TPVLayout`, `TPVController`, `TPVActions`.

- `kool_tpv/modulos/tpv/carrito/carrito_service.py`:
  - Cálculos de subtotal/iva/total correctos; gestión de descuentos y canje de
    puntos. Recomendación: aislar lógica de reparto de descuento por IVA en
    función pura y añadir tests unitarios.

- `kool_tpv/utils/formatter_service.py`:
  - Implementa patterns financieros (ROUND_HALF_UP). Recomendación: usar
    consistentemente este servicio en toda la app en lugar de cuantizar en
    lugares dispersos.

- `kool_tpv/utils/custom_dialog.py`:
  - Modular y reutilizable; buen manejo de fallback de iconos. Recomendación:
    externalizar estilos (colores, tamaños) a `config/colors_config.json`.

- `kool_tpv/config/buttons_config.json` y `buttons_actions_config.json`:
  - Definen la UI y comandos. Recomendación: validar JSON con schema al arranque
    y reportar errores de mapping al logger.

  UPDATE tickets SET num_ventas = COALESCE((SELECT COUNT(*) FROM ticket_lines WHERE ticket_id = OLD.ticket_id),0) WHERE id = OLD.ticket_id;

  UPDATE tickets SET num_ventas = COALESCE((SELECT COUNT(*) FROM ticket_lines WHERE ticket_id = NEW.ticket_id),0) WHERE id = NEW.ticket_id;
END;

D) `kool_tpv/base_datos/ticket_service.py` (detalle extendido)
- Responsabilidad:
  - Guardar ticket y líneas; actualizar stock y ventas; registrar pagos y puntos.
- Flujo clave (resumen):
  1. Inicia transacción explícita `BEGIN`.
  2. Calcula puntos a otorgar/restar usando `FidelizacionService`.
  3. Determina `num_ticket` con `SELECT MAX(num_ticket)` + 1.
  4. Construye `ticket_text_snapshot` con `VentaTicketGenerator` y guarda en DB.
  5. Inserta `ticket_lines`, actualiza `productos.stock_actual`, inserta
     `stock_movements` y `payments` según corresponda.
  6. Inserta `points_movements` y actualiza `clientes` (tesoro_total, historico).
  7. Inserta entrada en `audit_logs` (nota: columnas posiblemente incorrectas).
  8. Commit al final; rollback y log en excepciones.
- Riesgos y problemas detectados:
  - `SELECT MAX(num_ticket)` no garantiza atomicidad bajo concurrencia. En
    escenarios con múltiples TPVs conectados a la misma DB (o procesos
    simultáneos), pueden generarse duplicados.
  - Inserción a `audit_logs` utiliza columnas que no existen en schema, lo
    cual provoca excepciones (silenciadas) y pérdida de auditoría.
  - Uso de `str()` para persistir Decimals en algunas columnas y floats en otras
    genera mezcla de tipos; preferible normalizar antes de insertar.
- Recomendaciones técnicas inmediatas:
  1. Crear tabla `counters` con fila `key='num_ticket'` y operación atómica:
     UPDATE counters SET val = val + 1 WHERE key='num_ticket'; SELECT val;
     (en sqlite usar transaction para garantizar atomicidad local).
  2. Cambiar INSERT en `audit_logs` para usar columnas reales o añadir
     `ALTER TABLE` que añada las columnas necesarias con migración.
  3. Documentar contrato de tipos en DB: usar siempre strings para texto,
     Decimals convertidos a str al boundary y parseados en app cuando se lee.
  4. Añadir tests de stress/concurrency para `save_ticket` con threads que
     simulen ventas simultáneas.
