NOTAS ESPECÍFICAS SOBRE INCONSISTENCIAS DETECTADAS

- Inserciones en `audit_logs` realizadas por `ticket_service` no coinciden con
  las columnas presentes en la tabla `audit_logs` del schema; se debe alinear
  nombres o usar columnas explícitas en INSERT.
- `proveedores` es actualizado con `mapeo_csv` por `proveedor_service`, pero
  la columna no aparece en el extracto del schema — crear migración si procede.
- Referencias a tablas antiguas como `tickets_backup` y `clientes_old` sugieren
  que el schema actual contiene legacy constraints; revisar y limpiar.

ESTADO DEL PROYECTO (síntesis)

- TPV: core funcional. Carrito, cobro y generación de tickets operan en flujo
  normal. Reimpresión y cierres disponibles.
- Módulos (Almacén, Clientes): funcionales pero con algunas integraciones que
  requieren pruebas (import CSV, mapeo de proveedores).
- Persistencia: SQLite con estructura suficiente, triggers e índices, pero con
  campos esperados por el código ausentes o con nombres divergentes.

PRIORIDADES Y PLAN DE ACCIÓN (inmediato)

1) Corregir INSERT de auditoría en `ticket_service` para alinearlo con
   `audit_logs` real o alterar la tabla para mantener compatibilidad.
2) Añadir migración para `proveedores.mapeo_csv` si es necesaria.
3) Implementar test de integración `pytest` que persista tickets en DB
   `:memory:` y valide los efectos secundarios (tickets, ticket_lines,
   stock_movements, payments, points_movements).
4) Planificar refactor de `tpv_view.py` en subcomponentes (2-3 sprints).

CONCLUSIÓN

La base sobre la que está construida Kool TPV v2 es sólida: servicios por
entidad, uso de transacciones y separación en módulos. Las mejoras críticas
son de sincronización entre esquema y código, pruebas automáticas y
refactorización de UIs pesadas para mejorar mantenibilidad.

Si quieres, procedo a:
- Generar las migraciones SQL necesarias (ALTER TABLE) para conciliar campos
  detectados.
- Crear los tests de integración básicos para `save_ticket` con DB en memoria.
- Extraer y proponer un primer refactor de `tpv_view.py` por componentes.

--- NOTAS TÉCNICAS DETALLADAS (ARCHIVOS CRÍTICOS) ---

A continuación se amplían las observaciones técnicas sobre los archivos más
relevantes para el funcionamiento de la aplicación. Cada bloque incluye:
- Responsabilidad
- Flujo clave
- Riesgos detectados
- Sugerencias concretas de mejora (pasos accionables)

A) `main.py` (raíz)
- Responsabilidad:
  - Punto de entrada de la aplicación, configuración de `customtkinter` y
    logging, inicialización de la DB, creación de la ventana principal `App`.
- Flujo clave:
  - Se asegura carpeta `logs`, configura handlers (file + stdout).
  - Llama `initialize_database(db_path)` para aplicar migraciones si faltan
    tablas, luego instancia `Database(db_path)` y `db.connect()`.
  - Construye la navegación (lectura JSON `config/buttons_config.json`) y crea
    botones de la barra lateral con `ButtonFactory` si está disponible.
- Riesgos detectados:
  - Si `initialize_database` falla parcialmente, la app intenta continuar y
    podría obtener una conexión inválida a la DB; preferible abortar con
    mensaje claro en modo producción o debug según flag.
  - Importaciones tardías retrasan errores a runtime; recomendable test de
    arranque completo en CI para detectar import errors.
- Pasos de mejora concretos:
  1. Añadir `--headless` para inicializar sin UI (útil en CI).
  2. Validar `buttons_config.json` con schema JSON y fallar si inválido.
  3. Registrar versión del esquema DB en logs al iniciar para trazabilidad.

B) `kool_tpv/base_datos/db_wrapper.py`
- Responsabilidad:
  - Abstraer conexion sqlite y ofrecer helpers de consulta y contexto de
    transacción atómico.
- Flujo clave:
  - `connect()` asegura directorio padre y crea `sqlite3.Connection` con
    `detect_types` y `row_factory = sqlite3.Row`.
  - `transaction()` inicia `BEGIN`, hace `commit` o `rollback` según resultado.
- Riesgos detectados:
  - `check_same_thread=False` permite accesos desde múltiples hilos pero no
    resuelve problemas de concurrencia de escritura en SQLite (lock).
  - Falta de logging de latencia por query impide identificar consultas lentas.
- Pasos de mejora concretos:
  1. Añadir optional `query_logger` que emita log cuando una consulta tarda
     más de X ms.
  2. Exponer parámetro configurable `sqlite_kwargs` desde `config` para ajustar
     `timeout` y `journal_mode` si se requiere (WAL para concurrencia lectura/escritura).

C) `kool_tpv/base_datos/db_init.py`
- Responsabilidad:
  - Aplicar script de migración si faltan tablas críticas.
- Flujo clave:
  - Comprueba `sqlite_master` por tablas [`productos`, `tickets`, `cierres_caja`].
  - Si faltan, lee `migraciones/base.sql` y ejecuta `executescript`.
- Riesgos detectados:
  - `executescript` aplica múltiples statements atómicamente en sqlite, pero
    si el script está desactualizado respecto al código, el sistema quedará en
    un estado incoherente.
- Pasos de mejora concretos:
  1. Implementar tabla `schema_version` y migraciones incrementales (one-step
     migrations) en lugar de `base.sql` monolítico.
  2. Incluir checksum/version del script en el repo y validar que el script
     aplicado coincide con el esperado por la versión del código.

D) `kool_tpv/base_datos/ticket_service.py` (detalle extendido)
- Responsabilidad:
  - Guardar ticket y líneas; actualizar stock y ventas; registrar pagos y puntos.
- Flujo clave (resumen):
  1. Inicia transacción explícita `BEGIN`.
  2. Calcula puntos a otorgar/restar usando `FidelizacionService`.
  3. Determina `num_ticket` con `SELECT MAX(num_ticket)` + 1.
  4. Construye `ticket_text_snapshot` con `VentaTicketGenerator` y guarda en DB.
  5. Inserta `ticket_lines`, actualiza `productos.stock_actual`, inserta
     `stock_movements` y `payments` según corresponda.
  6. Inserta `points_movements` y actualiza `clientes` (tesoro_total, historico).
  7. Inserta entrada en `audit_logs` (nota: columnas posiblemente incorrectas).
  8. Commit al final; rollback y log en excepciones.
- Riesgos y problemas detectados:
  - `SELECT MAX(num_ticket)` no garantiza atomicidad bajo concurrencia. En
    escenarios con múltiples TPVs conectados a la misma DB (o procesos
    simultáneos), pueden generarse duplicados.
  - Inserción a `audit_logs` utiliza columnas que no existen en schema, lo
    cual provoca excepciones (silenciadas) y pérdida de auditoría.
  - Uso de `str()` para persistir Decimals en algunas columnas y floats en otras
    genera mezcla de tipos; preferible normalizar antes de insertar.
- Recomendaciones técnicas inmediatas:
  1. Crear tabla `counters` con fila `key='num_ticket'` y operación atómica:
     UPDATE counters SET val = val + 1 WHERE key='num_ticket'; SELECT val;
     (en sqlite usar transaction para garantizar atomicidad local).
  2. Cambiar INSERT en `audit_logs` para usar columnas reales o añadir
     `ALTER TABLE` que añada las columnas necesarias con migración.
  3. Documentar contrato de tipos en DB: usar siempre strings para texto,
     Decimals convertidos a str al boundary y parseados en app cuando se lee.
  4. Añadir tests de stress/concurrency para `save_ticket` con threads que
     simulen ventas simultáneas.

E) `kool_tpv/modulos/tpv/carrito/carrito_service.py` (detalle extendido)
- Responsabilidad:
  - Mantener estado del carrito, aplicar descuentos y canje de puntos,
    devolver resumen financiero con desglose de IVA.
- Flujo clave:
  - Items como dicts con `id`, `nombre`, `pvp` (Decimal), `cantidad`, `tipo_iva`.
  - `get_resumen_financiero()` calcula subtotal (sin IVA), desglose IVA por tipo,
    total IVA, aplica descuento y canje proporcionalmente entre tramos de IVA.
- Riesgos detectados:
  - Lógica de reparto de descuento es compleja y delicada numéricamente;
    necesita pruebas con decimales y casos borde (redondeos, devoluciones).
- Recomendaciones:
  1. Escribir testcases con ejemplos numéricos binarios (combinaciones de IVA
     4%/21%, descuentos en %, descuentos directos, puntos canjeados).
  2. Exponer funciones puras (ej. `recalcular_resumen(items, descuento, puntos)`) y
     testearlas en aislamiento.

F) `kool_tpv/utils/widgets/searchable_combo.py` (notas)
- Responsabilidad:
  - Proveer entrada con dropdown filtrable local o remoto.
- Observaciones técnicas:
  - Implementa dropdown con `tk.Toplevel` y `tk.Listbox` y bindings completos
    para navegación keyboard.
  - Mantiene `_last_results` cuando funciona en modo `search_function`.
- Riesgos:
  - Comportamiento del Toplevel y focus puede variar entre gestores de ventana;
    testear en macOS (el entorno del usuario) es crítico.
- Sugerencias:
  1. Implementar modo `test` con mock de `search_function` y headless.
  2. Documentar el contrato `search_function(text) -> list[{'id', 'nombre_display', ...}]`.

G) `kool_tpv/utils/templates/base_module_view.py` (notas)
- Responsabilidad:
  - Plantilla usada por módulos (sidebar, central area, breadcrumb y checks de
    cambios sin guardar).
- Observaciones técnicas:
  - `_check_unsaved_changes()` busca método `has_unsaved_changes` en los hijos
    lo cual es una convención útil; documentar esa convención para los UIs.
  - `set_central_content()` intenta ser robusto con distintos tipos de objetos,
    pero puede ocultar errores si muchos try/except silencian excepciones.
- Recomendaciones:
  1. Añadir logs DEBUG más descriptivos cuando `set_central_content` falla.
  2. Documentar patrón `has_unsaved_changes()` para implementadores de UIs.

H) `kool_tpv/modulos/impresion/venta_ticket_generator.py`
- Responsabilidad:
  - Generar representación textual del ticket para impresión y snapshot.
- Observaciones:
  - `ticket_service` intenta usar el generated text como `ticket_text_snapshot`.
  - Hay fallback a `ImpresoraService.generar_ticket_desde_id` si snapshot no existe.
- Recomendaciones:
  1. Unified contract: `generate(cfg, ticket_data, items, cliente)` debe devolver
     siempre string (no None) o lanzar excepción clara.
  2. Añadir tests templating con datos reales (artículos, descuentos, puntos).

I) `kool_tpv/modulos/impresion/impresora_service.py`
- Responsabilidad:
  - Abstracción de impresión; actualmente simula mediante `print()` si no hay
    impresora real.
- Observaciones:
  - Log de impresiones debería contener ticket_id y grave nivel INFO.
- Recomendaciones:
  1. Implementar queue de impresión asíncrona (Thread/Background) para no
     bloquear flujo de venta durante impresión física.

J) `kool_tpv/base_datos/producto_service.py` (puntos clave)
- Observaciones:
  - Las búsquedas paginadas usan subselects anidados y `GROUP_CONCAT`.
  - Si la tabla `ticket_lines` crece, `ventas` subselect puede ser costoso.
- Recomendaciones:
  1. Denormalizar contadores de ventas en `productos` (campo `ventas_totales`)
     y mantener con triggers (ya existe `ventas_totales` — verificar triggers
     y consistencia).
  2. Añadir índices en fields usados en WHERE/ORDER BY para mejorar búsqueda.
