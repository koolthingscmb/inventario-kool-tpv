3) Arquitectura general y flujo de ejecución
- La aplicación es una app de escritorio construida con `customtkinter` (CTk), con un `App` principal (`main.py`) que actúa como gestor de ventanas y punto de carga de módulos.
- Inicialización:
  - `App.__init__()` configura apariencia, fuentes, ventana, y crea `Database` usando ruta relativa a `kool_tpv/base_datos/kool_bd.db`.
  - `db.connect()` es llamado en el arranque y su conexión se guarda en `self.db`.
  - `create_navigation()` crea la barra lateral y carga configuración de botones desde `kool_tpv/config/buttons_config.json` si existe.
- Navegación modular:
  - Cada botón navega a un módulo (TPV, Almacén, Clientes, etc.) mediante carga perezosa (lazy import) para evitar dependencias circulares al inicio.
  - `load_tpv()` instancia `TpvView` pasando la conexión `db` y controla el tear-down (teardown) y visibilidad de botones (p. ej. ocultar navegación cuando se carga TPV).
  - `open_almacen()` demuestra patrón de embeber vistas en el root y usar callbacks para restaurar la UI de base.
- Persistencia y transacciones:
  - `kool_tpv/base_datos/db_wrapper.py` brinda acceso a SQLite con commit automático en `execute_query` y funciones `fetch_all`/`fetch_one`.
  - Las operaciones complejas como `save_ticket()` (en `ticket_service.py`) usan transacción explícita (`BEGIN`, `commit`, `rollback`) para asegurar atomicidad: inserción de ticket, líneas, movimientos de stock, pagos, auditoría y actualización de cliente/puntos.
- Integración impresión/fidelización:
  - `ticket_service.save_ticket()` integra generación de ticket mediante `VentaTicketGenerator` (si disponible) y el servicio de fidelización `FidelizacionService`.
- Diseño UI:
  - Se utiliza `CTkFrame` y `CTkButton` con estilos definidos centralmente (colores, fuentes). Se intenta seguir un sistema visual tipo "Matrix" (guía) con barra lateral de ancho 220px.

5) Servicios de base de datos: análisis detallado
- `db_wrapper.Database`:
  - Ventajas: wrapper simple y explícito que asegura creación de carpeta y manejo básico de errores.
  - Gap: no tiene manejo de `row_factory` ni conversores de tipos (Decimal), ni control de concurrencia. Conexión es directa `sqlite3.connect(self.db_path)` sin `check_same_thread` configurado ni `isolation_level` personalizado.
- `producto_service`:
  - Buen uso de `LEFT JOIN` sobre `precios` para obtener `pvp` activo y fallback a `0.0`.
  - Devuelve `pvp` como `str` para preservar precisión/serialización; adecuado si el código consumidor espera strings.
  - Tiene funciones `listar_productos`, `get_productos_by_tipo` y `get_productos_by_categoria` con manejo de excepciones y devoluciones limpias.
- `ticket_service.save_ticket`:
  - Implementación compleja y crítica: maneja transacción, cálculo de num_ticket, creación de `tickets`, `ticket_lines`, actualización de `productos.stock_actual` y `ventas_totales`, inserciones en `stock_movements`, `payments`, `audit_logs`, `points_movements` y actualización de `clientes`.
  - Uso de `Decimal` para evitar pérdidas por coma flotante; cuantiza valores monetarios a 2 decimales donde corresponde.
  - Manejo robusto de casos en los que tablas auxiliares no existen (usa try/except y logging.debug para inserts opcionales como `payments`, `audit_logs`, `points_movements`).
  - Genera `ticket_text_snapshot` si `VentaTicketGenerator` está disponible, lo que conecta la persistencia con la impresión.
  - Consideraciones de mejora: hay llamadas repetidas a `cur.execute('SELECT sku FROM productos WHERE id = ?')` dentro del bucle de líneas; podría reducirse con un SELECT previo o un JOIN para mayor eficiencia en tickets grandes.
  - Si un update de producto falla, el código registra y continúa; pero el rollback está a nivel superior: si ocurre excepción global se hace rollback. Esto es correcto pero hay puntos dentro del bloque que hacen `conn.rollback()` condicionalmente en sub-excepciones; hay que revisar la consistencia de rollback/raise.
- `cierre_service`:
  - Implementa `compute_totals_for_ticket_ids` y `create_cierre_atomic` que usa una transacción para insertar cierre y marcar tickets.
  - Realiza agregaciones por IVA leyendo `ticket_lines` y calculando base/iva por tipo, con conversión a floats para serialización.
  - Tiene lógica defensiva para DB con o sin columnas nuevas (fallback en caso de `OperationalError`).
- Otros servicios (`categoria_service`, `tipo_service`, `configuracion_service`): implementan queries simples y devuelven valores con manejo de excepciones.

6) Esquema de BD: correspondencia con el código (basado en `kool_bd_schema_2026-02-15.txt`)
- Tablas críticas observadas y su uso:
  - `productos`: columnas `id, nombre, sku, categoria, tipo, tipo_iva, stock_actual, ventas_totales, ...` — utilizadas en `producto_service` y `ticket_service` (update stock, select sku).
  - `precios`: columna `activo` usada para recuperar `pvp` activo en `producto_service`.
  - `tickets` y `ticket_lines`: estructura coherente con `ticket_service.save_ticket` (inserciones y referencias).
  - `stock_movements`: `ticket_service` intenta insertar registros si la tabla existe.
  - `points_movements`, `clientes`, `niveles_fidelidad`: usados por la fidelización.
  - `cierres_caja`: usado por `cierre_service`.
- Observaciones del schema:
  - Existen múltiples relaciones y triggers que mantienen `num_ventas` en `tickets` cuando se añaden/borra líneas (`trg_ticket_lines_*`). `ticket_service` también actualiza `ventas_totales` en `productos` directamente.
  - Indices importantes (`idx_precios_activo`, `idx_productos_categoria`, etc.) que mejoran rendimiento en consultas repetidas.
  - Algunas tablas hacen referencia a `tickets_backup` o `clientes_old` en `FOREIGN KEY` de `payments` y `points_movements`, lo que sugiere migraciones pasadas; el código usa defensivamente inserts en tablas opcionales.

10) Calidad del código, robustez y prácticas observadas
- Puntos positivos:
  - Uso extensivo de logging con distintos niveles (info, warning, exception) para diagnosticar errores.
  - Uso de transacciones en operaciones críticas (`save_ticket`, `create_cierre_atomic`).

- Áreas de mejora:
  - El wrapper `Database` es básico: añadir `row_factory`, conversores de Decimal, y contexto (context manager) mejoraría robustez.
  - Falta de tests unitarios que cubran `ticket_service` y `cierre_service` dado su carácter crítico.
  - Repetición de queries dentro de bucles (consultar `sku` por `id` por cada línea). Mejor hacer JOIN o bulk read.
  - Uso inconsistente de tipos: algunas funciones retornan strings para `pvp`, otras floats; estandarizar la API facilitaría integraciones.
  - Gestión de migraciones y esquema: `db_init.py` es placeholder; se necesitan scripts automáticos de migración para entornos nuevos.

11) Pros y Contras
- Pros (puntos fuertes):
  - Código modular y organizado por responsabilidades (UI, servicios, DB), lo que facilita extensión.
  - Implementaciones críticas (guardado de tickets, cierres) usan transacciones y manejo de errores.
  - Integración con módulos opcionales (impresión, fidelización) está pensada y con fallbacks.
  - Log detallado que facilita depuración.
  - Esquema de base de datos rico (puntos, cierres, auditoría, stock_movements) adecuado para un TPV profesional.
- Contras (puntos débiles):
  - Falta de pruebas automatizadas que validen flujos críticos.
  - `db_init.py` no automatiza la creación del esquema: riesgo en despliegues nuevos.
  - Inconsistencias en formatos de datos (strings vs Decimal/float) y ausencia de model layer que normalice tipos.
  - Potenciales problemas de concurrencia si la app se ejecuta en contextos multi-hilo/híbridos: sqlite sin opciones puede arrojar `sqlite3.ProgrammingError`.
  - Falta de componentes UI comunes que la `guia_estilo_blindaje` exige (SearchableCombo avanzado, Breadcrumbs, Grid 8 columnas), riesgo de inconsistencias visuales entre módulos.
