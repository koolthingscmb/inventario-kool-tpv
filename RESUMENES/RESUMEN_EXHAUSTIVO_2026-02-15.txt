2. Entrypoints y arranque de la app
---------------------------------
El arranque principal es `main.py` en la raíz. Observaciones:
- Se usa `customtkinter` para la interfaz (`ctk`).
- Se configura logging con archivo `logs/application.log`.
- Se crea instancia `Database` usando `kool_tpv/base_datos/kool_bd.db` (ruta relativa dentro del paquete).
- Tras conectar BD, se crea la UI principal `App` que monta una barra lateral (navegación) y un `main_frame` para vistas.
- Los botones de navegación se cargan desde `kool_tpv/config/buttons_config.json` con fallback a una lista hardcoded.
- `App.load_tpv()` crea/presenta la vista `TpvView` y gestiona el ocultado/restauración de botones y el botón `PRINT ON`.

Observaciones técnicas del arranque
- Se realizan imports perezosos (lazy imports) para evitar ciclos e improvisar cuando un módulo no está disponible.
- Se manejan excepciones con logs y fallbacks visibles para el usuario (labels de fallback en `main_frame`).
- El shutdown intenta cerrar la conexión DB (`db.close_connection()`) antes de `destroy()`.

3. Capa de persistencia (base_datos)
-----------------------------------
3.1 `db_wrapper.py`
- Implementa clase `Database` con métodos: `connect()`, `execute_query()`, `fetch_all()`, `fetch_one()`, `close_connection()`.
- Usa `sqlite3.connect(self.db_path)` directamente y commits manuales en `execute_query()`.
- Implementación sencilla y adecuada para SQLite en una sola instancia.

Puntos observados:
- No emplea `row_factory` ni `detect_types` de sqlite3: devuelve tuplas, lo que obliga a mapping manual en servicios.
- No hay control de concurrencia (locks) si la app escalase a multihilo/procesos (pero en UI Tkinter típico no hay concurrencia persistente sobre SQLite).
- No hay configuración de PRAGMA (journal_mode, synchronous) para robustez de BD en fallos: se podría mejorar.

3.2 `db_init.py`
- Archivo placeholder: no hay lógica de creación de esquema implementada aquí en la versión actual.
- Es recomendable que exista un script/función que cree tablas y relaciones (migraciones o SQL inicial) para facilitar instalación.

3.3 Base de datos en el repo
- Existen backups: `kool_bd.db.bak*` dentro de `kool_tpv/base_datos/`.
- Se espera que la app use `kool_bd.db` en esa ruta.

4. Servicios y lógica de negocio clave
------------------------------------
4.1 `producto_service.py`
- Métodos principales: `get_productos_by_categoria`, `get_productos_by_tipo`, `listar_productos`, `obtener_ventas_producto`.
- Usa `self.db.fetch_all()` y mapea resultados en listas de dicts con campos básicos (id, nombre, pvp, tipo_iva, stock, etc.).
- Buen manejo de `COALESCE` en SQL para evitar Nulls.

4.2 `ticket_service.py` (persistencia de tickets)
- Archivo con lógica compleja y núcleo crítico: `save_ticket(db, carrito_items, resumen, efectivo, cajero=...)`.
- Funcionalidad principal:
  - Inicia transacción explícita `BEGIN` y hace `conn.commit()` al final, `conn.rollback()` en errores.
  - Gestiona fidelización: usa `FidelizacionService` para calcular puntos ganados y restados.
  - Calcula `num_ticket` incrementando el max actual.
  - Usa `Decimal` para la contabilidad de importes, cuantiza a 2 decimales.
  - Inserta fila en `tickets` con snapshot `ticket_text` (generado por `VentaTicketGenerator` si está disponible).
  - Inserta `ticket_lines` por cada item, actualiza `productos.stock_actual` y `ventas_totales`.
  - Inserta movimientos de stock en `stock_movements` si existe la tabla (helper tolerante a ausencia de tabla).
  - Inserta líneas de descuento prorrateadas por tipo de IVA si hay descuento monetario `descuento_euros`.
  - Inserta pagos desglosados en `payments` si la tabla existe.
  - Inserta audit log en `audit_logs` si tabla existe.
  - Actualiza cliente (puntos/tesoro) y recalcula `id_nivel` de fidelidad si existen tablas relacionadas.

Observaciones críticas:
- El servicio es robusto en cuanto a manejo de excepciones y rollbacks, pero depende de la presencia de tablas opcionales (payments, stock_movements, points_movements, audit_logs). Usa inserciones tolerantes.
- El uso de `BEGIN` y `conn.commit()` es correcto; sin embargo, el `Database` wrapper no expone un manager de contexto ni transaction helper, lo que obliga a operar sobre `db.connection` desde servicios.
- Se mezclan concernes: lógica de puntos, creación de snapshot de ticket y persistencia están en la misma función — esto dificulta testabilidad y separación de responsabilidades.

4.3 `carrito_service.py`
- Implementa la gestión completa del carrito: `add_item`, `remove_item`, `update_cantidad`, `clear`, `get_items`, `get_subtotal`, `get_iva_desglose`, `get_resumen_financiero`, `apply_descuento`, `aplicar_canje_puntos`, etc.
- Usa `FormatterService` para formateo (no para cálculos) y `Decimal` para cálculos internos, lo cual es correcto.
- `get_resumen_financiero()` recalcula el efecto combinado de descuentos y puntos, prorratea descuentos entre tipos de IVA.

Observaciones del carrito:
- Buen uso de Decimal y separación entre datos (pvp, total_linea) y lógica de presentación.
- Soporta líneas de `devolucion` y comprueba restricciones (no permitir ventas si hay devolución activa).
- Tiene protección para no aplicar descuento si ya hay puntos canjeados (política de negocio). Esto está bien, pero es una regla de negocio que debe quedar documentada y testeada.

4.4 Fidelización y clientes
- Hay referencias a `FidelizacionService` (módulo `kool_tpv.modulos.clientes.fidelizacion_service`) utilizado en `ticket_service` y `tpv_view`.
- El flujo de puntos contempla: calcular puntos ganados por ventas, restar por devoluciones, y aplicar puntos canjeados como descuento monetario al guardar ticket.

7. Flujos críticos e integración
--------------------------------
7.1 Guardado de ticket (flujo crítico)
  - CarritoService acumula items -> CashController (o similar) llama a on_finalize -> llama a `ticket_service.save_ticket` con:
    * db (Database), items, resumen, efectivo/pagos, cajero, cliente y servicios auxiliares (fidelizacion_service, carrito_service)
  - `save_ticket` realiza transacción, inserta ticket, lineas, actualiza stock, inserta pagos y logs.
  - Tras éxito, `TpvView._on_finalize` limpia carrito y actualiza UI.

7.2 Devoluciones
  - Hay soporte para `DevolucionAction` que puede delegar la persistencia a su propio servicio. `TpvView` comprueba si hay líneas de devolución activas y delega si procede.

7.3 Impresión
  - Se genera un snapshot opcional (`ticket_text`) y se guarda en DB. `ImpresoraService` puede generar texto de ticket desde DB para imprimir o simular impresión en consola.

8. Calidad de código observada y puntos técnicos
----------------------------------------------
8.1 Buenas prácticas aplicadas
- Uso de Decimal para cálculos monetarios en `ticket_service` y `carrito_service`.
- Uso extensivo de try/except para robustez en entorno de UI donde faltan módulos.

8.2 Áreas con margen de mejora
- Falta de tests automáticos cubriendo flujos críticos (guardar ticket, actualizar stock, puntos).
- `db_wrapper` podría ofrecer context manager y helpers de transacción para centralizar commits/rollbacks.
- `db_init.py` vacío: falta una migración o script de inicialización, lo que dificulta reproducir entorno DB en instalación nueva.
- Mezcla de responsabilidades en `ticket_service.save_ticket` (persistencia, cálculo puntos, snapshot print, selección de configuraciones) — esto dificulta pruebas unitarias.

8.3 Observaciones de seguridad y consistencia
- No se han detectado entradas de usuario sin validar en SQL (uso de parámetros en consultas SQL, buena práctica presente).
- No hay controles de concurrencia para accesos a archivos DB en caso de múltiples procesos.

11. Pros y fortalezas
---------------------
- Arquitectura modular: separación por carpetas `modulos`, `base_datos`, `utils` facilita mantenimiento.
- Robustez y tolerancia a errores: abundantes try/except y fallbacks evitan crashes en producción.
- Uso correcto de `Decimal` para dinero y transacciones atómicas en `save_ticket`.
- Diseño UI pensado para TPV táctil (botones grandes, responsive, tipografías dedicadas).
- Persistencia de snapshot de ticket y hooks para impresión aumentan trazabilidad.

12. Contras y puntos débiles
---------------------------
- Falta de migraciones/initial schema (`db_init.py` vacío) — complicada instalación desde cero.
- `db_wrapper` es mínimo: no gestiona contexto, PRAGMA ni row_factory, lo que exige mapeos manuales.
- `save_ticket` es una función monolítica difícil de testear y con muchas responsabilidades.
- Poca cobertura de tests automatizados visibles en el repo (hay tests en `tests/` y `scripts/` pero no se ve un CI configurado aquí).
- Uso intensivo de cadenas como flags y comprobaciones por nombres de columnas; podría ocurrir regresiones silenciosas ante cambios en esquema.
- No hay validación central de permisos/roles en los controladores (p. ej. acceso a tickets) — hay placeholders.

13. Recomendaciones (técnicas y de producto)
------------------------------------------
Priorizar estas acciones por impacto/efuerzo:

Alta prioridad (0-3 semanas):
1) Implementar `db_init` o migraciones SQL
   - Crear script `kool_tpv/base_datos/schema.sql` y/o funciones Python que creen tablas necesarias.
   - Incluir PRAGMA recomendadas para SQLite: `journal_mode=WAL`, `synchronous=NORMAL` o `FULL` según necesidades.
   - Añadir verificación en arranque para aplicar migraciones pendientes.

2) Añadir transaction manager en `db_wrapper`
   - Proveer métodos `begin()`, `commit()`, `rollback()` o un context manager `with db.transaction():`.
   - Evitar acceso directo a `db.connection` desde los servicios; usar la API del wrapper para transacciones.

3) Modularizar `ticket_service.save_ticket`
   - Separar responsabilidades: 1) preparar datos (calcular puntos, descuentos), 2) persistir ticket y líneas, 3) actualizar cliente/puntos, 4) generar snapshot/print.
   - Hacer que cada paso sea testeable y que la función principal coordine y maneje rollback si alguna parte falla.

Mediana prioridad (3-8 semanas):
4) Añadir tests unitarios y de integración para flujos críticos
   - Tests para `CarritoService` (aplicar descuentos, canje de puntos, devoluciones).
   - Tests para `ticket_service` con DB en memoria (`:memory:`) y verificación de commits/rollbacks.
   - Tests UI básicos en modo headless para controladores (si es factible).

5) Mejorar `db_wrapper` para devolver rows como dicts
   - Usar `connection.row_factory = sqlite3.Row` o mapear columnas para evitar indexing por posición.

6) Documentación técnica mínima
   - README con pasos para instalación, variables de entorno, cómo restaurar DB desde backup y cómo ejecutar la app.
   - Documentar el esquema de BD (README o SQL comments).

Baja prioridad / mejoras continuas:
7) Introducir control de permisos y autenticación para acciones sensibles
   - Ejemplo: bloquear reimpresión/edición de tickets según roles.

8) Sistema de logging y métricas centralizado
   - Configurar rotación de logs y niveles por entorno.

9) Considerar migración a DB cliente-servidor si escala
   - Si crecimiento de concurrencia o múltiples terminales, valorar Postgres/SQLite en WAL con servidor intermedio.

-- TRIGGER trg_ticket_lines_after_delete
CREATE TRIGGER trg_ticket_lines_after_delete
AFTER DELETE ON ticket_lines
BEGIN
   UPDATE tickets SET num_ventas = COALESCE((SELECT COUNT(*) FROM ticket_lines WHERE ticket_id = OLD.ticket_id),0) WHERE id = OLD.ticket_id;
END

-- TRIGGER trg_ticket_lines_after_insert
CREATE TRIGGER trg_ticket_lines_after_insert
AFTER INSERT ON ticket_lines
BEGIN
   UPDATE tickets SET num_ventas = COALESCE((SELECT COUNT(*) FROM ticket_lines WHERE ticket_id = NEW.ticket_id),0) WHERE id = NEW.ticket_id;
END

-- TRIGGER trg_ticket_lines_after_update_ticketid
CREATE TRIGGER trg_ticket_lines_after_update_ticketid
AFTER UPDATE OF ticket_id ON ticket_lines
BEGIN
   UPDATE tickets SET num_ventas = COALESCE((SELECT COUNT(*) FROM ticket_lines WHERE ticket_id = OLD.ticket_id),0) WHERE id = OLD.ticket_id;
   UPDATE tickets SET num_ventas = COALESCE((SELECT COUNT(*) FROM ticket_lines WHERE ticket_id = NEW.ticket_id),0) WHERE id = NEW.ticket_id;
END
