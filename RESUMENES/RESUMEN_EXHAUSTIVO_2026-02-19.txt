**RESUMEN EJECUTIVO**

Kool TPV v2 es una aplicación de punto de venta escrita principalmente con `customtkinter` sobre Python, organizada en un paquete `kool_tpv` con separación en módulos funcionales (TPV, Almacén, Clientes, Impresión, Configuración). La app usa SQLite (`kool_bd.db`) como persistencia embebida y un `Database` wrapper para accesos y transacciones. El repositorio contiene utilidades UI reutilizables, servicios por entidad (producto, ticket, albarán, proveedor, etc.) y una configuración JSON que define la UI de navegación.

La revisión reitera que la arquitectura es modular y favorece la separación de responsabilidades, aunque varios archivos UI siguen mezclando layout y lógica, lo cual dificulta pruebas unitarias. El sistema implementa transacciones atómicas en puntos críticos (p. ej. `save_ticket`) pero usa prácticas en la numeración de tickets que pueden tener riesgos de colisión en entornos concurrentes. La guía de estilo interna («guia_estilo_blindaje.txt») establece estándares de UI y validación que el proyecto sigue parcialmente; recomiendan blindar componentes reusables (SearchableCombo, grid 8 columnas, atomicidad de guardado).

Este documento ofrece un recorrido detallado por los archivos que realmente participan en el funcionamiento de la app (excluye scripts de prueba inútiles y ficheros de basura). El objetivo es proporcionar un punto de partida técnico y operacional para tomar decisiones de refactorización, pruebas y despliegue.

**FLUJO DE ARRANQUE Y DEPENDENCIAS CRÍTICAS**

1. `main.py` (raíz) inicializa `customtkinter` y logging, asegura carpeta `logs` y llama `initialize_database(db_path)` si procede.
2. Se instancia la clase `App` (subclase de `ctk.CTk`), se configura la UI base (sidebar y main_frame) y se cargan los botones configurados en `config/buttons_config.json`.
3. Al demandar un módulo (p. ej. TPV o Almacén) se importan lazy las vistas correspondientes desde `kool_tpv.modulos.*`.
4. Las vistas principales (`BaseModuleView` y sus subclases) proveen `set_central_content()` para insertar widgets y actualizar breadcrumbs (cuando implementado).
5. `Database` es instanciada con la ruta a `kool_bd.db` y `connect()`.

Dependencias críticas: `customtkinter`, `Pillow` (para iconos), `sqlite3` (integrado), `kool_tpv.base_datos.db_wrapper.Database`.

Observaciones operacionales: los lazy imports reducen tiempo de arranque y evitan dependencias circulares al inicio, pero los errores en imports tardíos pueden ocurrir en runtime y deben registrarse claramente.

**ANÁLISIS DE LA PERSISTENCIA Y SCHEMA DE LA BBDD (ANEXO)**

Se incluye más adelante el dump (extracto) del schema de la base de datos `kool_bd.db` (extraído en la revisión previa). El schema contiene tablas para `productos`, `precios`, `tickets`, `ticket_lines`, `albaranes`, `albaran_lines`, `clientes`, `cierres_caja`, `stock_movements`, `points_movements`, `payments`, `audit_logs`, `categorias`, `tipos`, `proveedores`, `niveles_fidelidad`, índices y triggers para mantener `num_ventas` en `tickets`.

Puntos importantes sobre el schema y la persistencia:
- Se usan triggers para mantener contadores; esto es robusto pero complica migraciones si cambia la lógica.
- `num_ticket` se calcula ocasionalmente con `SELECT MAX(num_ticket)`, lo que no es seguro en entornos concurrentes; recomendación: tabla `counters` o mecanismo de secuencia.
- Uso mixto de tipos numéricos y `REAL` para importes: revisar consistencia y considerar `Decimal` en lógica de aplicación.
- Existen tablas para movimientos y auditoría que facilitan trazabilidad, buena práctica.

(El schema completo se encuentra en el anexo al final de este documento.)

**REVISIÓN POR MÓDULOS Y ARCHIVOS CLAVE**

A continuación se presenta una revisión técnica por módulos y por archivos considerados críticos para el funcionamiento. Para cada archivo se indica su responsabilidad, áreas de riesgo, observaciones y recomendaciones de mejora concretas.

1) `kool_tpv/main.py` (raíz)
- Responsabilidad: inicialización de la app, logging, DB init y creación de la barra lateral.
- Observaciones:
  - Buena separación entre UI y lógica de arranque.
  - Usa `initialize_database(db_path)` con try/except, escritura de logs a `logs/application.log`.
  - Maneja `print_on_button` y carga dinámica de `ButtonFactory`.
- Riesgos / mejoras:
  - El método `load_tpv()` intenta importar `TpvView`; errores en su importación se capturan pero conviene agregar mensajes más concretos para debugging.
  - Recomendación: añadir flag `--headless` o modo test para inicializar sin GUI y facilitar pruebas automáticas.

2) `kool_tpv/base_datos/db_wrapper.py`
- Responsabilidad: encapsular acceso a sqlite3 y ofrecer convenientes métodos de fetch/execute/transaction.
- Observaciones:
  - Implementa `transaction()` context manager — esencial para atomicidad.
  - Usa `check_same_thread=False` en la conexión lo que permite accesos desde hilos, pero hay que tener cuidado con concurrencia desde múltiples procesos.
- Riesgos / mejoras:
  - Añadir logs de queries lentas y métricas de tiempo para identificar cuellos de botella.
  - Verificar gestión de conexiones (pooling improbable con sqlite, pero cierre correcto es crítico).

3) `kool_tpv/base_datos/ticket_service.py`
- Responsabilidad: persistir tickets (ventas), actualizar stock, movimientos de puntos, payments y auditoría.
- Observaciones:
  - `save_ticket` encapsula muchos pasos; utiliza transacciones y snapshots.
  - Se usan try/except para tablas opcionales (payments, audit_logs), lo que facilita despliegues parciales.
- Riesgos / mejoras:
  - `SELECT MAX(num_ticket)` es susceptible a race conditions; usar una tabla `counters` o NUMBER generator centralizado.
  - Recomendación: estandarizar el uso de `Decimal` y convertir a STR únicamente en el boundary de la DB.
  - Agregar tests de concurrencia y casos extremos (descuentos, devoluciones, pagos mixtos).

4) `kool_tpv/modulos/tpv/tpv_view.py`
- Responsabilidad: UI principal del TPV; incluye orquestación del carrito, búsqueda de artículos y botones de pago.
- Observaciones:
  - Archivo muy extenso y con mezcla de layout y comportamiento; buena candidata a dividir en componentes (ActionPanel, ProductGrid, PaymentDialog, CarritoController).
  - Integra `BuscarArticuloPanel` que crea overlays; revisar uso de `place()` y tamaño para no chocar con versiones de `customtkinter`.
- Riesgos / mejoras:
  - Refactorizar en subcomponentes para aumentar la testabilidad.
  - Extraer la lógica de `ButtonFactory` y `BuscarArticuloPanel` para que sean testables en aislamiento.

5) `kool_tpv/modulos/almacen/almacen_view.py` y `kool_tpv/modulos/almacen/ui/albaranes_ui.py`
- Responsabilidad: vistas de Almacén y UIs de albaranes (entrada manual, consultar, detalle).
- Observaciones:
  - `AlmacenView` actúa como owner que ahora centraliza breadcrumbs y show_* métodos (se han añadido mapping y delegación). Arquitectura consistente.
  - `AlbaranesUI` es una UI que delega a `AlmacenView` para comportamiento, lo cual es correcto y reduce duplicación.
- Riesgos / mejoras:
  - Asegurarse que `ConsultarAlbaranUI` y `DetalleAlbaranUI` sean ligeros y reciban solo el `owner` necesario para callbacks.

6) `kool_tpv/modulos/clientes/` y `fidelizacion_service.py`
- Responsabilidad: gestión de clientes y aplicación de puntos (tesoro).
- Observaciones:
  - `FidelizacionService` es usado por `ticket_service` para computar puntos; revisar reglas (puntos por importe, redondeo, límites).
- Riesgos / mejoras:
  - Clarificar reglas de negocio y documentar invariantes (p. ej. la acumulación y caducidad de puntos).

7) `kool_tpv/modulos/impresion/` y `venta_ticket_generator`
- Responsabilidad: generar texto/plantilla del ticket y separar presentación de la persistencia.
- Observaciones:
  - `VentaTicketGenerator` produce snapshot textual usado por `save_ticket`.
- Riesgos / mejoras:
  - Añadir tests visuales y validación de templates con datos reales.

8) `kool_tpv/utils/` (templates, widgets, custom_dialogs)
- Responsabilidad: utilidades UI reutilizables y plantillas base.
- Observaciones:
  - `base_module_view.py` centraliza sidebar, breadcrumbs y `set_central_content()` lo cual deja la estética consistente.
  - `SearchableCombo` debería cumplir la guía de blindaje (navegación sin perder foco, validación strict mode).
- Riesgos / mejoras:
  - Refactorizar `SearchableCombo` y crear tests UI headless donde sea posible. Documentar API (get_id, validate).

9) `config/buttons_config.json` y `config/buttons_menu.json`
- Responsabilidad: parametrizar la navegación y acciones.
- Observaciones:
  - Sistema de `action_map` en `AlmacenView` remapeará strings a funciones; esto facilita extensibilidad sin tocar código.
- Riesgos / mejoras:
  - Validar schema JSON y añadir un linter/config validator para evitar errores de mapping.

**PRUEBAS Y COBERTURA**

- Existen scripts en `tests/` y `scripts/` para pruebas básicas. Sin embargo, la cobertura no es suficiente para:
  - `ticket_service.save_ticket` (escenarios de edge: devoluciones, pagos mixtos, concurrencia)
  - `CarritoService` (persistencia y rollbacks)
  - `SearchableCombo` (UI/validación)

Recomendación: añadir suite de pruebas de integración que use `:memory:` SQLite y mock de `VentaTicketGenerator`.

---

**CALIDAD DE CÓDIGO Y MANTENIBILIDAD**

- Estilo: mezcla de estilos; presencia de try/except amplios que mejoran robustez pero ocultan stack traces profundos.
- Tipado: escaso uso de typing en los módulos; recomendar añadir type hints en servicios y boundaries.
- Modularidad: buena separación por servicios; algunos archivos UI extensos requieren división.
- Documentación: falta documentación formal de APIs internas (servicios públicos), lo que dificulta onboard de nuevos desarrolladores.

---

**SEGURIDAD Y MANEJO DE DATOS**

- Datos sensibles (contrasenas de `usuarios`): almacenadas como texto en `usuarios.password` según schema. Recomendación: usar hash seguro (bcrypt/argon2) y no almacenar texto plano.
- Logs: contienen información de operaciones; cuidar que no se registre información sensible (tarjetas, datos personales) en texto plano.
- Acceso a BD: DB local (sqlite) no expuesta; si se migra a DB server, configurar ACL y cifrado en tránsito.

---

**RENDIMIENTO Y CONCURRENCIA**

- SQLite soporta concurrencia limitada (lock por escritura). Para tiendas con múltiples procesos/terminales simultáneos, considerar migrar a PostgreSQL o añadir un servicio central de facturación.
- Monitorear queries lentas: añadir logging y metrics para identificar cuellos.

---

**PROS Y CONTRAS (RESUMEN)**

Pros:
- Arquitectura modular y servicios bien separados.
- Uso correcto de transacciones en operaciones críticas.
- UI basada en `customtkinter` con plantilla central (`base_module_view`) que asegura coherencia estética.
- Presencia de auditoría y movimientos que facilitan trazabilidad.

Contras:
- Archivos UI muy grandes mezclando layout y lógica.
- Puntos críticos con potencial de race conditions (`SELECT MAX(num_ticket)`).
- Almacenamiento de contraseñas en texto (riesgo).
- Cobertura de tests insuficiente en servicios cruciales.
- Uso de try/except amplio que puede ocultar errores en fases tempranas.

---

**RECOMENDACIONES (PRIORITIZADAS)**

Corto plazo (1-2 semanas):
- Añadir tests unitarios/integración para `ticket_service.save_ticket` usando DB `:memory:`.
- Forzar hashing de contraseñas en `usuarios` y añadir utilidades de login.
- Añadir validación JSON para `buttons_config.json`.

Medio plazo (1-3 meses):
- Refactorizar `tpv_view.py` en subcomponentes y mover lógica a servicios testeables.

- Reemplazar `SELECT MAX(num_ticket)` por tabla `counters` o mecanismo seguro.

Largo plazo (6-12 meses):
- Evaluar migración a PostgreSQL si hay necesidad de concurrencia multiproceso/multiserver.
- Añadir CI con tests aislados (pytest + sqlite :memory:), linters y pre-commit.
- Revisar y documentar el esquema de migraciones e introducir versión de esquema.

---

**PLAN DE MIGRACIÓN / OPERACIONES**

- Mantener SQLite para entornos de una sola instancia; para multi-terminal, definir plan de migración a DB cliente/servidor.
- Definir scripts de backup/restore de `kool_bd.db` con retención y verificación de checksum.

-- trigger trg_ticket_lines_after_delete
CREATE TRIGGER trg_ticket_lines_after_delete
AFTER DELETE ON ticket_lines
BEGIN
  UPDATE tickets SET num_ventas = COALESCE((SELECT COUNT(*) FROM ticket_lines WHERE ticket_id = OLD.ticket_id),0) WHERE id = OLD.ticket_id;
END

-- trigger trg_ticket_lines_after_insert
CREATE TRIGGER trg_ticket_lines_after_insert
AFTER INSERT ON ticket_lines
BEGIN
  UPDATE tickets SET num_ventas = COALESCE((SELECT COUNT(*) FROM ticket_lines WHERE ticket_id = NEW.ticket_id),0) WHERE id = NEW.ticket_id;
END

-- trigger trg_ticket_lines_after_update_ticketid
CREATE TRIGGER trg_ticket_lines_after_update_ticketid
AFTER UPDATE OF ticket_id ON ticket_lines
BEGIN
  UPDATE tickets SET num_ventas = COALESCE((SELECT COUNT(*) FROM ticket_lines WHERE ticket_id = OLD.ticket_id),0) WHERE id = OLD.ticket_id;
  UPDATE tickets SET num_ventas = COALESCE((SELECT COUNT(*) FROM ticket_lines WHERE ticket_id = NEW.ticket_id),0) WHERE id = NEW.ticket_id;
END
