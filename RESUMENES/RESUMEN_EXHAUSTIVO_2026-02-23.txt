RESUMEN EJECUTIVO

Kool TPV v2 es una aplicación de punto de venta implementada en Python y
`customtkinter` que organiza la funcionalidad en un paquete `kool_tpv` dividido
por capas: persistencia (SQLite), servicios por entidad, módulos UI (TPV,
Almacén, Clientes, Impresión), utilidades y assets. La arquitectura es modular
pero pragmática; la separación ayuda a localización de responsabilidades, pero
existen áreas donde la lógica de negocio se mezcla con la construcción de UI,
lo que dificulta pruebas unitarias y mantenimiento.

Puntos críticos observados:
- La persistencia principal usa SQLite con un wrapper (`db_wrapper.Database`) que
  permite transacciones y acceso multi-hilo (`check_same_thread=False`). Esto
  es práctico para un entorno monolítico pero plantea limitaciones si se
  desea concurrencia multi-terminal real: SQLite ofrece concurrencia limitada
  y la generación de `num_ticket` mediante `SELECT MAX(num_ticket)` provoca
  potenciales duplicados en escenarios con paralelismo real.
- `ticket_service.save_ticket` agrupa muchas responsabilidades (cálculo de
  puntos, actualización de stock, inserción de payments, audit logs, snapshot
  de impresión), lo que beneficia atomicidad pero aumenta la complejidad
  y el coste de testing integrado.
- Varios UIs, especialmente `tpv_view.py`, son monolitos que mezclan layout y
  lógica de negocio; conviene romperlos en controlador + presentación.
- Se observa uso consistente de `Decimal` en cálculos monetarios y funciones
  helper como `FormatterService` que garantizan redondeo coherente.

Objetivo del documento: ofrecer una guía precisa del estado del repositorio,
explicar la función de cada componente principal, exponer el schema de la BD,
identificar riesgos y proponer un plan de corrección priorizado.

FLUJO DE ARRANQUE Y COMPONENTES CRÍTICOS

1) Inicialización
- El entrypoint `main.py` configura logging (archivo `logs/application.log` + stdout),
  establece apariencia `customtkinter`, crea `App` (ventana principal) y conecta
  la base de datos principal `kool_bd.db`.
- `initialize_database(db_path)` (en `kool_tpv/base_datos/db_init.py`) se ejecuta
  para aplicar `migraciones/base.sql` si faltan tablas críticas.

2) UI principal
- `App` construye barra lateral y botones de navegación según
  `kool_tpv/config/buttons_config.json`. Los módulos se importan de forma lazy
  para evitar dependencias cíclicas durante arranque.

3) Módulos dinámicos
- Al seleccionar una sección (TPV, Almacén, Clientes), el `App` crea la vista
  correspondiente (`TpvView`, `AlmacenView`, `ClientesView`), que publica
  interacciones con servicios y la `Database`.

4) Persistencia transaccional
- `db_wrapper.Database` provee `transaction()` context manager para agrupar
  commits y rollbacks.
- Operaciones críticas (guardar ticket, guardar albarán, cierre de caja)
  se realizan dentro de transacciones explícitas.

Componentes críticos:
- `db_wrapper.Database`: centraliza la conexión y transacciones.
- `db_init.py`: aplica migraciones; si falla deja la app en riesgo.
- `ticket_service.save_ticket`: operación compleja y crítica para integridad.
- `tpv_view.py` y `CarritoService`: manipulan la experiencia de cobro.

REVISIÓN POR CAPAS (hallazgos y recomendaciones sintetizadas)

Persistencia (`kool_tpv/base_datos`)
- Calidad: código estructurado: wrapper + servicios. Uso de transacciones y
  triggers es un punto fuerte.
- Riesgos: generación de `num_ticket` con `MAX()` y uso de SQLite cuando se
  requiere concurrencia real.
- Recomendaciones:
  * Implementar tabla `counters` para secuencias atómicas locales.
  * Versionar migraciones (tabla `schema_version`) y aplicar migraciones
    incrementales en vez de `base.sql` monolítico.
  * Añadir logging de queries lentas y métricas.

Servicios (producto, ticket, albaran...)
- Calidad: la separación por entidad facilita mantenimiento.
- Riesgos: `ticket_service.save_ticket` es muy grande; tests unitarios e
  integración insuficientes en áreas críticas.
- Recomendaciones:
  * Extraer subresponsabilidades del save_ticket a funciones testables.
  * Añadir test de integración con sqlite `:memory:`.

UI y módulos
- Calidad: interfaz completa con widgets reutilizables.
- Riesgos: archivos UI largos con lógica embebida; dificil de testear.
- Recomendaciones:
  * Refactor en `View` (presentación) + `Controller` (lógica), ver patrón MVC.
  * Testear componentes puros (FormatterService, CarritoService, VentaTicketGenerator).

Utilidades y config
- Recomendar validar JSON de configuración en arranque y documentar contratos.

Seguridad y permisos
- Almacenamiento de `usuarios.password` en BD: asegurar hashing (bcrypt/argon2).
- Revisar permisos de archivos y logs que contienen datos sensibles.

ANÁLISIS DETALLADO POR ARCHIVO (extractos y observaciones)

A continuación se exponen secciones ampliadas sobre archivos clave. Para cada
archivo se indica: responsabilidad, flujo relevante, riesgos detectados y
recomendaciones de mejora concretas.

1) `kool_tpv/base_datos/db_wrapper.py`
Responsabilidad:
- Proveer conexión y helpers de consulta (fetch_all/fetch_one/execute_query).
- Proveer context manager `transaction()` para operaciones atómicas.

Flujos relevantes:
- `connect()` crea la carpeta padre si no existe y se conecta con
  `sqlite3.connect(self.db_path, **self._sqlite_kwargs)`; por defecto
  `check_same_thread=False` y `timeout=10`.
- `execute_query()` hace commit automático; `transaction()` permite
  BEGIN/COMMIT/ROLLBACK manual controlado.

Riesgos:
- `check_same_thread=False` permite acceso multi-hilo, pero las escrituras
  concurrentes en SQLite pueden provocar bloqueos si no se diseñan medidas
  complementarias (WAL, timeouts adecuados).

Recomendaciones:
- Añadir `pragma journal_mode = WAL` en la inicialización (opcional y con
  pruebas) para mejor concurrencia lectura/escritura en algunos escenarios.
- Añadir `query_logger` opcional para log de queries lentas (> threshold ms).
- Documentar uso de `:memory:` para tests.

2) `kool_tpv/base_datos/db_init.py`
Responsabilidad:
- Detectar tablas críticas y aplicar `migraciones/base.sql` si faltan.

Flujos:
- Consulta `sqlite_master` para detectar tablas y aplica `executescript(sql)`.

Riesgos:
- Falta de versionado: si el script cambia y la BD está en estado parcial puede
  quedar inconsistencia.

Recomendaciones:
- Implementar `schema_version` y migraciones incrementales (cada migration con
  `up` y `down`). Herramientas: Alembic (si se migra a Postgres) o un pequeño
  migrator propio.

3) `kool_tpv/base_datos/ticket_service.py`
Responsabilidad:
- Guardar tickets y efectos colaterales: líneas, stock, pagos, puntos, audit log.

Flujo:
- Inicia transacción explícita con `BEGIN`.
- Calcula puntos con `FidelizacionService`.
- Determina `num_ticket` como `SELECT MAX(num_ticket) + 1`.
- Inserta ticket y líneas en `ticket_lines`.
- Actualiza stock y `ventas_totales` en `productos` y registra en `stock_movements`.
- Inserta `payments` (efectivo/tarjeta), `points_movements` y actualiza `clientes`.
- Inserta `audit_logs` y recalcula `id_nivel` de fidelidad.
- Commit o rollback.

Riesgos detectados:
- Race condition por `SELECT MAX(num_ticket)`.
- Inserciones a tablas accesorias silenciadas cuando fallan (puede ocultar
  problemas de compatibilidad de schema).
- Mezcla de tipos (strings/decimals/floats) que puede complicar migraciones.

Recomendaciones:
- Reemplazar `MAX(num_ticket)` por tabla `counters` o mecanismo de incremento
  atómico dentro de la misma transacción.
- Asegurar que `audit_logs` INSERT coincide con schema (revisar columnas).
- Normalizar conversión Decimal <-> DB en un helper central.
- Añadir pruebas que simulen concurrencia con hilos locales en `:memory:`.

4) `kool_tpv/base_datos/producto_service.py`
Responsabilidad:
- CRUD y búsquedas de productos con filtros y paginación.

Observaciones:
- Devuelve precios como strings para preservar precisión — buena práctica
  para evitar problemas de conversión en la UI.
- `buscar_productos_paginados` combina `GROUP_CONCAT` y subselects; puede
  volverse lento en tablas grandes.

Recomendaciones:
- Revisar índices en `productos.sku`, `precios(producto_id, activo)` y
  `ticket_lines.sku` para mejorar performance.
- Considerar denormalizar contadores si se necesita escala.

5) `kool_tpv/modulos/tpv/carrito/carrito_service.py`
Responsabilidad:
- Modelar el carrito en memoria: add/update/remove, calcular subtotal, IVA,
  aplicar descuentos y canje de puntos.

Observaciones:
- Uso consistente de Decimal y `FormatterService` para rounding.
- Lógica de reparto de descuento por tipo de IVA es correcta pero compleja;
  requiere tests para casos límite.

Recomendaciones:
- Exponer funciones puras (stateless) para los cálculos críticos y testarlas
  con pytest (ej: `repartir_descuento_por_iva(items, descuento)`).
- Añadir validaciones en la API pública del servicio (ej: `add_item` valida id
  del producto; se pueden reforzar contratos).

6) Widgets `searchable_combo`, `ticket_display`, `textview_dialog` etc.
Observaciones:
- Buen nivel de reutilización; `SearchableCombo` soporta `search_function`
  callback para búsquedas remotas o locales.
- Toplevel/focus y event binding requieren pruebas cross-platform (Windows,
  macOS, Linux) para garantizar UX.

Recomendaciones:
- Añadir tests con `tkinter` headless mocks o scripts de integración UI si se
  precisa validar visual behaviors.

7) Config JSONs (`kool_tpv/config`)
Observaciones:
- Botones, paletas de colores y menús parametrizados en JSON permiten ajustes
  sin tocar código.

Recomendaciones:
- Validar JSON con `jsonschema` al arranque y fallback sensible en caso de
  error para evitar crashs en producción.

INCONSISTENCIAS DETECTADAS Y ACCIONES CORRECTORAS SUGERIDAS

1) Numeración de tickets:
- Problema: `SELECT MAX(num_ticket)` usado para asignar `num_ticket`.
- Impacto: duplicados en escenarios con concurrencia o reinicio parcial.
- Solución: crear tabla `counters(key TEXT PRIMARY KEY, value INTEGER)` y
  usar:
    with db.transaction() as cur:
        cur.execute("UPDATE counters SET value = value + 1 WHERE key = 'num_ticket'")
        cur.execute("SELECT value FROM counters WHERE key = 'num_ticket'")
  Esto garantiza atomicidad local en SQLite.

2) Audit logs malformed insert:
- Problema: `ticket_service` inserta en `audit_logs` columnas que no existen.
- Acción: revisar `INSERT` y cambiar a INSERT explicito con las columnas
  existentes o migrar la tabla para añadir campos usados.

3) Passwords en claro:
- Problema: `usuarios.password` parece ser texto plano según schema.
- Acción: aplicar migración para rehash y forzar hashing en creación/actualización
  de usuarios; añadir `password_salt` si se necesita.

4) Migraciones:
- Problema: `db_init` aplica un script monolítico; no hay `schema_version`.
- Acción: diseñar sistema de migraciones incremental sencillo (aplicar solo
  scripts sin ejecutar todo `base.sql` salvo en creación desde cero).

5) Tests insuficientes para `save_ticket`:
- Acción: escribir tests de integración con DB `:memory:` cubriendo:
  * Pagos mixtos
  * Canje de puntos
  * Devoluciones
  * Concurrencia simulada con threads (para validar counters)
